# Workflow Watchdog - 后台任务巡检

## 适用场景

适用于宿主允许监督、且调用方有实际检查和停止权限的普通 CLI、长批处理或其他非原生自动完成通知任务。这类子进程可能卡在循环或重试里，需要有界监督。

**原生 `task(background=true)` 且具有自动完成通知的 subagent 不适用定时巡检。** 按 [并行 Subagent 工作流](./workflow_parallel_subagents.md) 等待自动完成通知；不得通过定时 wake-up、轮询、`sleep` 查进度或定时读取日志绕过该约束。派发前把阶段预算、总 deadline、日志、失败停止条件与部分产物留存安排在子任务内部或平台明确支持的事件通道中。

## 做法

对上述允许监督的任务，派发前明确阶段与产物、总 deadline、无进展预算及日志位置。长批处理可将约 30 分钟（1800s）作为巡检间隔参考，但不能用它替代任务自身的时限，也不能放任交互阶段长时间无反馈。仅使用当前宿主实际提供且授权使用的机制；例如支持时使用 `ScheduleWakeup`，或按已安装的 Process Launcher skill 安排延时监督，不编造工具。

在获准的检查点核对同一任务与本次尝试的进展，而不只看进程是否存活。启动 receipt 不是完成证明；验收还须核对实际结果与产物。分两种情况处理：

1. **真实在忙**：有可核对的阶段进展或新产物；在总 deadline 内继续，确需再检查时保持有界。日志增长本身不等于有效进展。
2. **卡住、明确失败或超时**：先保留失败阶段、日志、退出码（如有）、diff 与部分产物，再按权限仅停止本次调用所属的进程。利用已有结果收窄下一步，不在没有新证据时原样重复大任务。

在上述范围内自主判断进展并处理恢复，遵守既有权限与 `rules/SOUL.md` 的自主执行契约；不得因此停止无关进程或扩大授权。对原生自动通知 subagent，恢复仍走其子任务内部预算与平台支持的事件机制，不新增宿主轮询。

## 来源

实践反馈：跑 workflow 时子进程卡住，AI 死等浪费了整段时间。教训是派发前明确监督与恢复边界；只有允许宿主监督的任务才安排有界巡检，不覆盖原生自动完成通知的 no-poll 契约。
